# 监控界面与声音压制方案

> 状态：技术研究与交互草案 v0.1  
> 日期：2026-10-03

## 1. 结论

“自动调音量”和“压制音频信号”是两个不同层级：

1. **系统音量控制**：监测系统混音，持续偏响时降低当前输出设备的主音量。实现相对简单、延迟影响小，适合作为第一版。
2. **音频 DSP 压制**：把所有系统音频先送入我们的处理链，执行增益骑乘、动态压缩和峰值限制，再送到真实输出设备。控制精确，但需要接管音频路由，平台实现与安装复杂度明显更高。

第一版建议使用系统音量控制，并把界面、指标、日志和控制算法做好。真正 DSP 作为独立验证阶段，不能把“降低系统音量”宣传成“已经实现实时限制器”。

## 2. 监控界面信息结构

### 2.1 首页必须直接回答的五个问题

| 用户问题 | 界面字段 |
|---|---|
| 现在到底多响？ | 当前 Short-term LUFS、Momentary LUFS、峰值 dBFS/dBTP |
| 系统音量现在是多少？ | 当前系统音量百分比和设备名称 |
| 自动系统改了多少？ | 用户基准音量、当前执行音量、自动修正量 |
| 为什么正在调整？ | 当前状态和一条明确动作原因 |
| 什么设置在生效？ | 触发阈值、目标区间、最低/最高系统音量、速度 |

不能只显示“调整后音量”。建议采用以下三个值，避免混淆：

- **用户基准音量**：用户最近一次主动设定、设备档案恢复或本次自动控制开始时的参考值。
- **当前系统音量**：操作系统当前真实值，也是用户按系统音量键看到的值。
- **自动修正量**：当前系统音量相对用户基准的变化，例如 `-9 个百分点`；如果设备支持可靠的 dB 映射，再同时显示 `-3.2 dB`。

### 2.2 首页布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 当前设备        自动调节开关        状态 / 暂停原因          │
├───────────────────┬───────────────────┬──────────────────────┤
│ 当前响度          │ 当前系统音量      │ 自动修正              │
│ -17.8 LUFS        │ 58%               │ -9 个百分点           │
│ 峰值 -3.1 dBFS   │ 用户基准 67%      │ 持续偏响，正在压低    │
├───────────────────────────────────────┬──────────────────────┤
│ 最近 60 秒响度、目标区间、调整事件   │ 快速设置              │
│                                       │ 触发阈值              │
│                                       │ 目标响度区间          │
│                                       │ 最低 / 最高系统音量   │
│                                       │ 压低 / 恢复速度       │
├───────────────────────────────────────┴──────────────────────┤
│ 最近动作：14:32:08 系统音量 61% → 58%，原因：连续 4.2 秒偏响 │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 设置字段

| 设置 | 面向用户的含义 | 初版交互 |
|---|---|---|
| 自动调节 | 是否允许程序写系统音量 | 总开关；关闭后继续监控 |
| 触发响度 | 多响时开始压低 | LUFS 滑杆；必须显示单位和解释 |
| 目标响度区间 | 希望持续内容落在哪个范围 | 双端范围；不是系统音量百分比 |
| 峰值保护阈值 | 突然峰值多高时触发快速下降 | 高级设置；单位 dBFS，DSP 模式可用 dBTP |
| 最低系统音量 | 自动控制不得低于此值 | 百分比滑杆 |
| 最高系统音量 | 自动恢复不得高于此值 | 百分比滑杆 |
| 压低速度 | 持续偏响时下降多快 | 慢 / 平衡 / 快，展开后显示数值 |
| 恢复速度 | 偏轻时回升多快 | 默认明显慢于压低速度 |
| 手动让路时长 | 用户调音量后暂停多久 | 秒数或“直到下次播放稳定” |
| 只自动压低 | 禁止程序主动升高系统音量 | 第一版默认开启 |

目标响度与系统音量上限必须分开：前者描述监测到的声音，后者描述程序允许触碰的系统旋钮范围。

### 2.4 状态和提示

界面固定使用可解释状态，不用模糊的“智能处理中”：

- `只监控`：正在测量，不写系统音量。
- `目标范围内`：自动模式开启，但当前无需动作。
- `正在压低`：显示触发值、持续时长和本次调整量。
- `缓慢恢复`：显示恢复条件和最高允许值。
- `用户接管`：显示倒计时；此时不写音量。
- `重新校准`：设备刚切换，控制暂停。
- `设备不可控制`：保留监测，解释为何不能写系统音量。
- `监测已暂停`：权限、捕获或设备故障。

最近 60 秒趋势至少包含：Short-term loudness 曲线、目标区间、触发线、系统音量曲线和自动动作标记。默认不显示大量频谱或音乐特征。

## 3. 声音压制的三层方案

### 3.1 层级 A：系统主音量增益骑乘

```text
系统混音监测 → 响度误差 → 平滑与安全约束 → 改系统主音量
```

适合解决：不同歌曲、视频、网页之间持续数秒以上的音量落差。

优点：

- 可以利用现有 macOS Core Audio tap 和 Windows WASAPI loopback 监测能力。
- 不需要重新输出音频，通常不会增加可感知的音频延迟。
- 崩溃时不会截断声音；最多留下最后一次系统音量值，可在退出时恢复。

局限：

- 第一个突然峰值已经播放后才能观察到，无法当作真正的 brick-wall limiter。
- 系统音量步进和声学增益不是简单线性关系，需要按设备校准。
- 修改主音量会影响同一设备上的所有应用，必须尊重用户手动操作。
- 如果捕获点位于主音量之前，监测值不会随调节变化，必须用设备增益映射估算或降级。

第一版采用这一层，并默认“只自动压低”。

### 3.2 层级 B：慢速增益骑乘加动态压缩

```text
捕获并接管系统混音
    → 1–3 秒尺度的响度增益骑乘
    → 中等时间尺度的宽带压缩器
    → 输出到真实设备
```

增益骑乘负责来源之间的长期差异，压缩器只处理持续过响部分。微软对 Loudness Equalization 的说明也是“感知响度测量 + 动态增益调整”，采用较快的衰减和较慢的恢复，以保留部分短时动态。

实验起始值只能作为测试参数，不是最终默认值：

- 触发依据：Short-term loudness 持续超过目标上沿。
- 压缩比：从温和的 `2:1` 开始比较。
- Attack：约 `20–100 ms` 范围内试听。
- Release：约 `500–2000 ms` 范围内试听。
- Makeup gain：默认关闭，避免压低后又把整体推高。

主要风险是 pumping、呼吸感、鼓点被削弱和背景噪声被抬起。参数必须通过盲听和波形/响度日志一起评估。

### 3.3 层级 C：峰值限制器

```text
压缩后音频 → 数毫秒 look-ahead → 峰值限制 → 输出
```

限制器用于防止处理后的音频超过数字上限，不能代替响度控制。EBU R128 将 Programme Loudness、Loudness Range 和 Maximum True Peak 作为不同描述量，这也是界面不应把 LUFS 和峰值混为一个滑杆的原因。

实验建议：

- 使用小型 look-ahead 缓冲才能在峰值真正输出前衰减；这会增加端到端延迟。
- ceiling 从保守的 `-1 dBTP` 实验值开始，不直接承诺为产品标准。
- 记录 gain reduction，出现长时间大幅限制时应降低前级增益，而不是持续“顶住”限制器。

## 4. 真正 DSP 压制为何更难

监听系统输出不等于能够修改系统输出。DSP 模式需要让原始声音不再直达扬声器，同时把处理后的声音重新送到真实设备，否则会出现原声和处理声重叠。

### 4.1 macOS

可验证的方向：

```text
Core Audio global tap
  + muted / mutedWhenTapped
  → 实时 DSP
  → AUHAL / 输出 Audio Unit
  → 当前真实输出设备
```

Apple 的 `CATapMuteBehavior` 明确支持捕获时不把被 tap 的音频继续送往硬件；系统也提供 Dynamics Processor 和 Peak Limiter Audio Units。因此 macOS 可以先做一个不安装虚拟音频驱动的技术试验。

仍需验证：全局 tap 静音覆盖、排除本程序避免反馈、蓝牙/HDMI 路由、设备时钟漂移、输出格式变化、睡眠唤醒、权限撤销以及进程崩溃后是否立即恢复原声。任何一项不可靠，都不能成为默认模式。

### 4.2 Windows

WASAPI loopback 只能复制当前 shared-mode 渲染流用于监听，不能阻止原声继续输出；exclusive-mode 也不能使用 loopback。因此“回录 → 处理 → 再播放”会产生双声，不能直接作为正式方案。

Windows 的正式系统级 DSP 插入点是 Audio Processing Object（APO）。Endpoint Effect 可以作用于使用同一端点的所有流，但自定义 APO 是实时 COM 组件，需要与驱动包和 INF 安装/注册一起交付，并满足非阻塞、低延迟等实时约束。它属于单独的驱动级项目，不应混进第一版监控工具。

备选路线是提供自有虚拟输出设备，让用户把它设为系统输出，再由应用处理后播放到真实设备；这同样涉及驱动安装、设备切换和卸载恢复，不比普通桌面功能轻量。

### 4.3 跨平台决策

| 方案 | macOS | Windows | 第一版结论 |
|---|---|---|---|
| 调系统主音量 | 可行，按设备能力降级 | 可行，EndpointVolume | 采用 |
| 捕获后直接处理再播放 | 可用 tap mute 方向做技术试验 | loopback 会保留原声 | 不作为共同方案 |
| 系统级 DSP 插件/驱动 | Audio Server Plug-in/虚拟设备方向 | APO/虚拟设备方向 | 独立长期阶段 |
| 使用系统已有“响度均衡” | 能力与入口不统一 | 部分设备可能提供 | 只能探测和提示，不能作为产品核心 |

## 5. 推荐控制策略

### 5.1 第一版

1. 实时监测 Short-term LUFS、Momentary LUFS、RMS 和峰值。
2. 当前值持续超过触发阈值后，快速但分步降低系统音量。
3. 当前值回到目标区间后保持，不来回追踪。
4. 只有确认不是静音、暂停或淡出时，才允许极慢恢复。
5. 默认禁止自动升到用户基准以上，并受最高系统音量限制。
6. 用户手动调节、设备切换、捕获异常时立刻停止写入。

### 5.2 后续 DSP 模式

只有平台路由验证通过后，才增加：

1. 慢速响度增益骑乘；
2. 温和宽带压缩；
3. 最后的峰值限制器；
4. DSP bypass 与崩溃恢复；
5. 端到端延迟、gain reduction 和漏音监控。

## 6. 开发与验收重点

### 6.1 界面验收

- 当前系统音量必须直接读取操作系统，不能只是程序内部预测值。
- 自动修正必须能追溯到一次具体动作和触发原因。
- 调整设置后，控制器使用的实际值和界面显示一致。
- 只监控、自动调节和未来 DSP 模式有清晰不同的状态标识。
- 设备不可控时相关设置禁用，并给出可操作说明。

### 6.2 音质与安全验收

- 安静段、淡出和暂停不会导致音量爬升。
- 稳定单音、宽动态音乐、强鼓点、对白、通知音分别测试。
- 不出现原声与处理声重叠、声道反转、采样率错误或周期性咔哒声。
- 处理线程超时、设备断开或程序退出时优先恢复可听原声。
- A/B 试听分别记录“更稳定”和“动态被破坏”两个判断，不能只看数值变平。
