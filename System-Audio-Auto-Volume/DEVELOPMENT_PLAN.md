> 状态：M0–M2 已完成；M3–M4 只读原型已实现、验收门禁进行中  
> 日期：2026-10-03  
> 范围：macOS + Windows 系统级自动音量 MVP

## 1. 交付目标

第一版交付一个本机运行的系统音量监控与自动调节工具：

- 实时显示当前输出设备、系统实际音量、响度、峰值和最近 60 秒趋势；
- 可以设置触发响度、目标区间、音量上下限、压低/恢复速度和手动让路；
- 支持只监控、影子决策、只自动压低三个安全等级；
- 支持 macOS 和 Windows，设备不可控时自动降级；
- 不保存原始音频，不依赖歌曲身份，不训练模型；
- 第一版不承诺真正的压缩器或 brick-wall limiter。

## 2. 已锁定的开发原则

1. **先读后写**：先完成真实监控，再允许程序写系统音量。
2. **先影子后闭环**：控制器先只记录“本来会怎么调”，通过回放和实际试听后才执行。
3. **先只降后回升**：第一版自动控制默认只能降低；自动回升是独立门禁。
4. **控制环与界面分离**：界面刷新卡顿不能影响音频采集和控制决策。
5. **实时回调只做轻量工作**：不在音频回调中写文件、调用 UI、阻塞或运行模型。
6. **没有可靠反馈就不闭环**：设备不提供可写音量或回录不响应音量变化时，只监控。
7. **不提前做桌面壳**：MVP 使用本机后台服务和本地网页；稳定后再决定托盘应用。
8. **DSP 单独立项**：捕获后压缩/限幅需要音频路由，不能与主音量 MVP 混为一个完成条件。

## 3. MVP 技术形态

### 3.1 进程结构

```text
平台音频适配器
  ├─ macOS：Core Audio tap + 输出设备监听
  └─ Windows：WASAPI loopback + EndpointVolume 监听
          ↓
实时电平计算
  ├─ RMS / Peak（先实现）
  └─ Momentary / Short-term loudness（验证后启用）
          ↓
共享控制器
  ├─ 状态机
  ├─ 静音门和目标区间
  ├─ 用户接管与设备切换
  └─ 只监控 / 影子 / 只降低 / 完整自动
          ↓
平台音量适配器
          ↓
本机状态 API → 监控网页
```

### 3.2 最小技术选择

| 部分 | MVP 选择 | 原因 |
|---|---|---|
| 后台与共享控制器 | Python | 与现有 Windows 录音工具和测试体系一致，便于快速验证 |
| 数值计算 | NumPy，仅在确实需要时使用 | 本地已有；适合处理 PCM 数组，不增加新模型依赖 |
| macOS 采集/设备 | Swift Core Audio helper | 复用现有系统输出 tap 经验，使用原生权限和设备 API |
| Windows 采集 | PyAudioWPatch / WASAPI loopback | 现有代码和测试已经验证基础路径 |
| Windows 音量控制 | EndpointVolume 最小适配器 | 能读写端点主音量并接收变更通知 |
| 监控界面 | 单页 HTML/CSS/JS | 与现有 dashboard 方式一致，跨平台且易于调试 |
| 界面通信 | 本机 HTTP 状态接口，先轮询 | 4 Hz 左右足够显示；控制环独立运行，不需要先上 WebSocket |
| 配置 | 单个版本化 JSON | 可审计、可迁移，不引入数据库 |
| 日志 | JSONL 事件摘要 | 可回放控制决策，不保存音频内容 |

不在 MVP 中引入 Electron、Tauri、数据库、消息队列或机器学习框架。

## 4. 核心数据契约

先固定最小契约，避免 macOS、Windows 和界面各自解释状态。

### 4.1 状态快照 `system-audio.state/v1`

至少包含：

- 时间戳、平台、匿名设备 ID、设备显示名；
- 捕获状态、控制能力、权限和错误；
- RMS dBFS、Peak dBFS；
- 经验证后加入 Momentary/Short-term LUFS；
- 当前系统音量、用户基准音量、自动修正量；
- 控制模式、状态机状态、最后动作和原因；
- 当前生效设置版本。

缺失的测量值必须为 `null` 并带原因，不能伪造成 `0`。

### 4.2 设置 `system-audio.settings/v1`

至少包含：

- `mode`：`monitor` / `shadow` / `lower-only` / `automatic`；
- 触发响度、目标区间；
- 最低/最高系统音量；
- 压低速度、恢复速度；
- 手动让路时长；
- 设备级覆盖设置；
- schema 版本和更新时间。

所有写入在服务端校验：上下限不能反转，目标区间不能反转，速度与等待时间必须在安全范围内。

### 4.3 动作事件 `system-audio.action/v1`

每次决策记录：

- 监测证据；
- 原音量、建议音量、实际写入音量；
- 动作来源：自动、用户、设备变化或恢复；
- 不执行时的阻止原因；
- 控制器版本和设置版本。

## 5. 开发阶段与门禁

### M0：冻结契约与测试场景

任务：

- 确认上述三份 JSON 契约；
- 建立不含版权音频的合成测试信号：静音、稳定音量、阶跃变响、阶跃变轻、短峰值、渐弱；
- 固定状态机名称和设置校验规则；
- 明确第一版只自动压低。

产物：契约 fixture、控制场景表、参数说明。

通过门禁：同一份 fixture 能被服务、控制器测试和界面读取；所有缺失值处理明确。

### M1：共享控制器离线回放

任务：

- 实现纯函数状态机，不接真实设备；
- 输入按时间排列的电平与用户/设备事件，输出动作建议；
- 实现静音门、滞回、最小持续时间、音量边界、用户让路；
- 建立最小自动测试。

必须通过的场景：

- 安静段、暂停和渐弱不建议升音量；
- 短峰值不导致连续大幅调整；
- 持续偏响产生有限步长的下降建议；
- 用户手动操作后停止自动建议；
- 设备切换后进入重新校准；
- 设置异常被拒绝。

产物：共享控制器、离线回放 CLI、测试。

通过门禁：控制器不依赖操作系统、音频设备或网页即可完整测试。

### M2：模拟数据监控界面

任务：

- 建立本机服务和单页监控界面；
- 接入模拟适配器，输出可重复的 60 秒状态序列；
- 实现当前响度、系统音量、用户基准、自动修正和动作原因；
- 实现设置读取、校验、保存和恢复；
- 界面刷新与控制循环分离。

接口先保持最小：

- `GET /api/status`
- `GET /api/history`
- `GET /api/settings`
- `POST /api/settings`
- `POST /api/mode`

产物：可交互监控页、本机 API、模拟适配器。

通过门禁：不接任何真实系统音频，也能演示全部状态与设置；刷新页面不会丢失已保存设置。

### M3：macOS 真实监控，只读

任务：

- 从现有 Core Audio tap 提取最小采集能力，不写录音文件；
- 识别默认输出设备、设备切换和权限变化；
- 输出 RMS、峰值、回调延迟和丢帧；
- 只读取系统音量，不修改；
- 验证扬声器、有线/USB、蓝牙和数字输出的能力差异。

产物：macOS 只读适配器、设备能力报告、真实监控界面。

通过门禁：连续运行 60 分钟无回调停止或内存持续增长；设备切换能停止旧数据并进入重新校准。

### M4：Windows 真实监控，只读

任务：

- 从现有 PyAudioWPatch 录音工具提取 loopback 流，不落盘；
- 匹配当前默认渲染端点和 loopback；
- 读取 EndpointVolume 与静音状态；
- 监听默认设备切换、端点断开和音量变化；
- 明确 shared-mode 与 exclusive-mode 的失败表现。

产物：Windows 只读适配器、设备能力报告、真实监控界面。

通过门禁：与 macOS 输出相同的状态契约；同名设备不会错误匹配；设备异常能明确降级。

### M5：响度指标校准

RMS/Peak 可先显示；只有此阶段完成后，界面和控制器才正式使用 `LUFS` 名称。

任务：

- 实现或引入最小的 K-weighting 与 400 ms / 3 s 窗口；
- 用 Flowset/FFmpeg `ebur128` 作为离线参照，不放入实时主循环；
- 在 macOS、Windows 使用同一批合成信号和合法测试音频交叉验证；
- 测量 CPU、延迟、窗口启动和静音门行为。

产物：指标误差报告、性能报告、经验证的 meter 测试向量。

通过门禁：实时值在两个平台的允许误差内一致；未通过前只能显示 RMS/Peak，不能伪称 LUFS。

### M6：音量控制适配器，人工触发

任务：

- macOS：探测并读写当前输出设备的可写音量属性；
- Windows：通过 EndpointVolume 设置主音量并标记本程序事件上下文；
- 识别用户操作与程序操作；
- 验证音量步进、静音、设备切换和退出行为；
- 完成每个设备的“小幅响应校准”。

此阶段只有界面上的人工测试按钮可以写音量，控制器仍不能自动执行。

退出策略：只有在当前值仍等于本程序最后写入值、期间没有用户接管时，才允许恢复基准音量；否则保持用户当前值。

产物：两平台音量适配器、设备校准记录、人工写入测试。

通过门禁：失败设备准确标记为只监控；任何错误都不会循环写音量或覆盖用户新设置。

### M7：影子模式

任务：

- 使用真实音频与真实系统音量运行控制器；
- 生成“建议调整”但不执行；
- 界面同时显示实际音量和建议音量；
- 收集不同内容和设备上的误触发、漏触发、建议频率。

产物：影子模式事件日志、可回放报告、参数调整记录。

通过门禁：人工复核通过安静段、切歌、通知音、对白、宽动态音乐和手动操作；没有持续升高建议。

### M8：只自动压低闭环

任务：

- 只执行降低动作；
- 设置保守的最低/最高边界和每秒最大变化量；
- 每次动作显示原因，并提供立即暂停；
- 设备变化、权限变化、捕获异常立即停止写入；
- 对控制频率、抖动和听感进行日常测试。

产物：第一版可用闭环、动作日志、跨平台测试报告。

通过门禁：连续日常使用中没有意外上调、没有音量来回抖动、用户手动操作立即生效。

### M9：可选的缓慢恢复

任务：

- 只在非静音、非暂停、非淡出且长时间低于目标时允许恢复；
- 不超过用户基准和设备最高限制；
- 恢复速度明显慢于压低速度；
- 作为独立开关，默认关闭直到试听通过。

产物：`automatic` 模式。

通过门禁：所有“音量爬升”测试通过，用户确认恢复节奏自然。

### M10：包装与日常运行

任务：

- 决定是否封装托盘应用；
- 加入单实例、正常退出、崩溃恢复和日志轮换；
- 分别生成 macOS 与 Windows 的可撤销安装/运行说明；
- 开机启动保持可选且默认关闭。

产物：可分发本地版本、安装/卸载说明、已知限制。

通过门禁：卸载后不遗留虚拟设备、系统扩展或自动启动项；MVP 本身不应安装这些内容。

## 6. DSP 压制分支

MVP 完成后再开独立技术分支，不阻塞 M0–M10：

### D1：macOS 路由试验

- global tap 使用 `mutedWhenTapped` 或等价模式；
- 排除本程序输出，避免反馈；
- 接入慢速 gain rider、温和压缩器和 peak limiter；
- 测量端到端延迟、漏音、时钟漂移、设备切换与崩溃恢复。

### D2：Windows 方案选择

只做两条路线的技术评估：

- 自定义 APO；
- 自有虚拟输出设备。

比较驱动签名、安装权限、升级/卸载、端点兼容、低延迟和维护成本。WASAPI loopback 监听后直接重放不进入候选，因为无法阻止原声输出。

### D3：是否产品化的门禁

只有同时满足以下条件才进入正式开发：

- 两个平台都有可靠且可撤销的路由；
- 崩溃不导致持续静音；
- 不出现原声和处理声重叠；
- 延迟适合音乐和视频；
- 压缩/限幅能通过盲听，不明显破坏音乐动态；
- 用户明确接受额外权限和安装复杂度。

## 7. 测试矩阵

### 7.1 内容

- 静音和暂停；
- 低电平持续声音；
- 从低到高的音量阶跃；
- 从高到低的音量阶跃；
- 短通知音和单次峰值；
- 宽动态音乐；
- 持续高响度音乐；
- 对白、网页视频和多个来源切换；
- 淡入、淡出和曲间空白。

### 7.2 设备

| 平台 | 至少覆盖 |
|---|---|
| macOS | 内置扬声器、3.5 mm/USB、蓝牙、一个不可写音量的数字输出场景 |
| Windows | 内置/主板输出、USB、蓝牙、同名端点、默认设备切换、shared/exclusive 差异 |

### 7.3 故障

- 拒绝或撤销捕获权限；
- 输出设备断开；
- 默认设备切换；
- 音频回调停止或超时；
- 平台 helper 退出；
- 本机 API 或页面关闭；
- 设置文件损坏；
- 用户在自动调节期间按音量键；
- 应用异常退出后重新启动。

## 8. 每个阶段的统一完成条件

每个里程碑结束前必须同时满足：

1. 有一个最小、可重复的自动检查；
2. 异常路径不会写错音量或丢失用户设置；
3. 日志不包含原始音频和歌曲内容；
4. macOS/Windows 契约字段含义一致；
5. 新参数在界面、配置、控制器和日志中一致；
6. 文档记录已验证行为和未验证边界；
7. 未通过门禁不得提前开启下一等级的自动控制。

## 9. 第一轮实际工作包

开始编码时只做 M0–M2，不碰真实系统音量：

1. 写状态、设置和动作 JSON fixture；
2. 写控制器的六类合成时间序列测试；
3. 实现只监控/影子状态机；
4. 建立本机状态 API；
5. 将已确认的监控界面接入模拟数据；
6. 验证设置保存、刷新恢复和动作解释。

第一轮验收后，再分别开始 M3 macOS 和 M4 Windows 真实监控。这样可以在没有平台权限、驱动和设备差异干扰的情况下，先把产品行为定义正确。

## 10. MVP 完成定义

只有以下条件全部成立，才称为跨平台 MVP 完成：

- macOS 与 Windows 都能稳定读取当前输出设备的系统混音摘要；
- 监控界面显示真实系统音量、用户基准、自动修正、目标和动作原因；
- 设置经过服务端校验并能安全持久化；
- RMS/Peak 准确，显示为 LUFS 的指标已完成跨平台校准；
- 两个平台都通过设备切换、用户接管和故障降级测试；
- 影子模式报告经过人工复核；
- `lower-only` 模式通过日常使用，没有自动升高和明显抖动；
- 程序退出或崩溃不会持续占用音频设备或导致静音；
- 没有保存、上传或训练任何系统音频内容；
- 真正 DSP 压缩/限幅仍明确标记为后续独立能力。
